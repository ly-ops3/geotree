# 数据型开源项目的"clone 即部署"：pg_dump、种子分发与 Docker 编排

geo-registry 是个典型**数据型**项目：代码两千行，数据八十多万行。
对这类项目，"clone 下来跑不起来"的第一死因永远不是代码，而是数据。
这篇记一下为部署链路做的几个决定。

## pg_dump：为什么不用 pgAdmin

pgAdmin 的导出功能能用，但它把 job 历史存在自己的 profile 目录里
（`%APPDATA%\pgAdmin`），而且 GUI 操作天然不可重复。命令行 `pg_dump`
没有任何状态，可以写进脚本、README、Makefile，这是基础设施操作该有的形态：

```bash
pg_dump -U postgres -d geo_registry -t geo_places -Fc -f geo_places.dump
```

## -Fc 压缩格式 vs 纯文本 SQL

两种导出形态，用法和适用面完全不同：

| 格式 | 体积 | 还原工具 | 适用 |
|------|------|----------|------|
| 纯文本（默认） | 大 | `psql -f`，还能直接 `grep` | 小表、需要肉眼检查的种子 |
| `-Fc` 自定义压缩 | 小一个数量级 | `pg_restore` | 大表、纯传输分发 |

`geo_places` 87 万行，`-Fc` 出来 21.5MB。还原时注意幂等参数：

```bash
pg_restore -U postgres -d geo_registry --clean --if-exists geo_places.dump
```

`--clean --if-exists` = 有旧表先删再建，可重复执行不炸——部署脚本的第一美德是幂等。

## 大文件进不进 git：我的判断标准变了

最初我把 35MB 的 `zh_altnames.sqlite` 和 21.5MB 的 `geo_places.dump`
都 gitignore 了，理由是"二进制大文件不该进仓库、数据是可再生产物"。
被一句话问醒：**"31M 都入了，21M 凭什么不入？"**

重新想这个决策，真正的判断标准不是"多大"或"能不能再生"，而是
**用户拿到仓库后第一小时要做什么**：

- 项目是工具型（编译器、框架）→ 数据应该外挂，clone 要轻
- 项目是数据型（本项目）→ 数据就是本体，clone 完还得跑半小时
  `import_all.py` 联网下载 GeoNames 才能用的仓库，等于没交付

GitHub 单文件硬上限 100MB，两个文件加起来 57MB 远未触线。
最终决定：**seed 目录全量入库，`database/backups/` 整个忽略**——
前者是"分发物"，后者是"本地保险"。

## 数据许可：开源数据也要署名

仓库里混了三种来源的数据，公开前必须把账算清：

- GeoNames gazetteer/alternateNames：**CC-BY 4.0，强制署名**
- CLDR 行政区中文名：Unicode License
- ok_zh 国内区划：GitHub 开源四级区划数据集（行政区划公开统计信息）

README 里加了"数据来源与许可"一节。开源数据不是无主数据，
"从 GitHub 拿的"不等于可以无署名再分发——CC-BY 的要求很低，
一行 attribution 就合规，不写就是你理亏。

## Docker：三个服务的依赖链

`docker-compose.yml` 用 service 依赖条件串起整个初始化流程，
不需要任何 shell 胶水：

```yaml
services:
  db:    # postgres:18-alpine + healthcheck(pg_isready)
  seed:  # 同一个 postgres 镜像当一次性灌库容器
    depends_on: { db: { condition: service_healthy } }
    volumes:  [ "./database/seed:/seed:ro" ]
    command: [ sh, -c, "psql -f /seed/ok_zh_level4.pgdump.sql &&
                        pg_restore --clean --if-exists /seed/geo_places.dump" ]
    restart: "no"
  api:
    depends_on: { seed: { condition: service_completed_successfully } }
    environment: { GEO_DB_DSN: postgresql://postgres:postgres@db:5432/geo_registry }
```

两个值得一提的点：

1. **seed 直接复用 postgres 镜像**——不需要为灌库专门造镜像，
   `psql`/`pg_restore` 都在里面，`restart: "no"` 跑完即退
2. **数据库连接走环境变量**——代码侧本来就支持
   `GEO_DB_DSN` 覆盖 config.json，容器里完全不需要配置文件，
   密码不落盘

镜像里 `COPY . .` 会把 57MB 的种子数据也打进去，换来的是镜像
自包含——对数据型服务来说这笔体积是值回票价的。

## 彩蛋：数据里到底有几国语言？

顺手扫了 `name_local` 的文字分布（87.4 万条）：

| 文字系统 | 条数 |
|----------|------|
| 拉丁字母（无重音） | 622,876 |
| 拉丁字母（带重音符：法德西葡意的 é/ü/ñ…） | 157,032 |
| 空 | 93,990 |
| 西里尔 | **56** |
| 阿拉伯文 | 7 |

所以"支持多语言"要诚实：拉丁语系用户是**真受益**（法国人能直接搜
"Île-de-France"，因为 name_local 就是本地名），但西里尔/阿拉伯/日韩
用户搜母语地名基本没戏——GeoNames alternateNames 里其实有其他语言
别名，只是我只入库了中文。README 里放了 10 语种一句话简介，
前 6 个是真服务，后 4 个是门面。想补齐的话把 alternateNames 全量
按语言灌进索引就行，留给以后。
